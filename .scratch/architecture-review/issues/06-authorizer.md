# Single Authorizer owns wildcard, owner, trusted and fallback rules

Status: resolved
Strength: Worth exploring

The `CommandContext` dependency part was split out to [10](10-command-context-deps.md) on 2026-09-28.

## Files
- `auth/Permission.kt:38` (`AuthResult.hasPermission`) and `game/session/PlayerSession.kt:34`
  (`PlayerSession.hasPermission`): two identical bodies
- `Permission.WILDCARD` checked inline: `GameLoop.kt:1020` (visible-command filter), `:1731` (command gate),
  `:1921` (no-token-store fallback), `ClaimManager.kt:100`, `:124`, `Claim.kt:39`, `HubConnection.kt:153`,
  `AdminController.kt:732`
- Owner-or-permission cascade hand-rolled three times: `ActionBlockService.kt:158`, `PanelManager.kt:62`,
  `ActionBlockEditCommand.kt:130` (this last one never consults the Claim)
- Claim edit rights are two layers: `Claim.canEdit` (owner / trusted / `*`) and `ClaimRegistry.canEdit`
  (the above plus faction ally, via a post-construction `factionAlly` var wired in `GameWorldFactory.kt:379`
  and `GameLoop.kt:588`)

## Problem
- **Hub sessions get the Account's permissions.** `HubConnection` builds a `PlayerSession` from
  `authResult?.permissions` where `GameLoop` resolves the Character's RBAC groups. ADR-0006 says the two never
  share permissions. The `?: setOf(Permission.WILDCARD)` fallback there also applies when a token store exists
  but the auth result is null.
- **No RBAC group can override a Claim.** Claims test `WILDCARD` in hard code where Action blocks and Panels use
  a named permission, so a moderator group cannot be granted claim access — only `*` can.
- `GameLoop` runs two separate command-permission gates (visible-command filter, execution gate) with no test
  holding them in agreement.
- `/actionblock edit` ignores the Claim its target sits in, while interacting with the same block respects it.
- "No token store = full access" is written three times.

## Solution
An `Authorizer` that owns the composite cascade (named permission → owner → Claim → faction ally) behind one call,
named Claim permissions for build and administer, and a single point where a session's permissions are resolved.

## Tests
`PlayerSessionTest`, `PermissionTest`, `ClaimTest` and `AdminControllerAuthTest` cover the current behaviour; nothing
asserts parity between the two command gates, nor between a hub session and a direct session.

## Decisions (2026-09-28)

1. **Scope**: in-game authorization on the Character. `AuthResult.hasPermission` keeps its signature and the Admin
   role catalog stays separate (ADR-0006); only the "`*` covers everything" rule is shared, as one primitive both
   entry points delegate to.
2. **Two Claim rights**: `claim:build` and `claim:administer`, neither implying the other. `administer` covers
   abandoning a Claim and editing its trusted list; `build` covers break / place / interact / action blocks.
3. **`Authorizer` names the composite, not the primitive.** `hasPermission` keeps its name and its 14 call sites.
4. **Typed target, not nullable arguments**: `EditTarget` is a sealed type (`ByOwner`, `InWorld`, `OwnedInWorld`);
   the Claim lookup happens inside the Authorizer for the variants carrying a position.
5. **Single permission-resolution point** at session construction, shared by the direct and hub paths. The admin
   HTTP short-circuit stays separate because it concerns the Account.
6. **`/actionblock edit` is aligned** on the interaction path — an intentional behaviour change.
7. **No new ADR**: ADR-0006 is extended, `CONTEXT.md`'s Claim entry is updated. Both done on 2026-09-28.
8. **`factionAlly` wiring** collapses to a single site here; turning it into a constructor dependency belongs to
   [04](04-gameworld-self-assembly.md).

## Agent Brief

**Category:** enhancement (carries one security defect)
**Summary:** One Authorizer owns the permission cascade; Claim overrides become grantable through RBAC groups; every
session path resolves the Character's permissions the same way.

**Current behavior:**

Authorization rules are spread across the server. The `*` wildcard is tested inline in the command gates, in Claim
edit checks and in Claim administration checks, in parallel with a `hasPermission` helper that already handles it.
The cascade "named permission → owner → Claim" is written by hand in three places, and the three disagree: the
Action block command path ignores the Claim its target sits in, while the interaction path honours it.

Claim rights are the only ones with no named permission, so a Character can only override a Claim by holding `*`. No
RBAC group can carry that override, which contradicts ADR-0006.

Session permissions are resolved differently depending on how the session opens. The direct connection path resolves
the Character's RBAC groups; the hub companion path takes the permissions off the auth result — the Account's — and
falls back to a full wildcard set whenever that result is absent, including when authentication is configured.

**Desired behavior:**

A single authorization module owns every composite decision. Callers ask it one question and never re-derive the
rules. It resolves, in order: the named permission on the session (wildcard included, through the existing
primitive), then ownership of the target, then the Claim covering the target's position, including faction-ally
access.

Claims gain two named permissions, one for building and one for administering, neither implying the other.
Administering means abandoning a Claim or changing its trusted list, and remains restricted to the owner and to
Characters whose groups grant it — a trusted Character or a faction ally may build but never administer. Building
covers breaking, placing, interacting and editing Action blocks inside the Claim.

Every path that opens a session resolves that session's permissions from the Character's RBAC groups through one
shared function. The "no auth backend configured" fallback that grants full access exists in exactly one place and
applies only when no token store is configured; a configured token store with no auth result grants nothing.

The two command gates — the one filtering which commands a Character is shown, and the one admitting a command for
execution — answer from the same call, so a command can never be listed and refused, nor hidden and runnable.

**Key interfaces:**

- An `Authorizer` type exposing a single composite check taking the session, the required `Permission`, and a target.
- `EditTarget`: a sealed type with a `ByOwner` variant (owner name known, no position), an `InWorld` variant
  (position known, no owner) and an `OwnedInWorld` variant. No nullable owner or position parameters on the
  Authorizer's signature.
- Claim permissions registered through `PermissionRegistry` like the Action block and Panel ones, so they appear in
  the permission catalog and can be listed in `groups.yaml`.
- `PlayerSession.hasPermission` and `AuthResult.hasPermission`: signatures unchanged, both delegating the wildcard
  rule to one shared function. The Character catalog and the Admin role catalog stay distinct.
- A single session-permission resolution function, taking the token store presence, the groups config and the
  Character's groups, returning the permission set. Both the direct and hub session paths call it.
- A single command-eligibility check used by both the visible-command filter and the execution gate.

**Acceptance criteria:**

- [x] A Character in an RBAC group holding the Claim build permission, and holding no `*`, can break and place
      inside another Character's Claim.
- [x] That same Character cannot abandon that Claim nor change its trusted list.
- [x] A Character in a group holding the Claim administer permission, and holding no `*`, can abandon another
      Character's Claim, and this does not by itself let them build there.
- [x] A trusted Character and a faction ally can still build in the Claim and still cannot administer it.
- [x] A Character holding `*` retains today's behaviour on every Claim operation.
- [x] A hub companion session and a direct session for the same Character resolve to the same permission set, and
      that set comes from the Character's RBAC groups, not from the auth result.
- [x] With a token store configured and no auth result, a session is not granted the wildcard permission.
- [x] With no token store configured, a session is granted full access, and the code expressing that rule exists in
      one place.
- [x] Editing an Action block through its slash command applies the same Claim rules as interacting with it: a
      Character with neither ownership nor the Action block permission nor Claim build rights is refused on both.
- [x] A test walks the command registry and asserts, for at least one permission set that is neither empty nor
      wildcard, that the visible-command filter and the execution gate agree on every command.
- [x] `Permission.WILDCARD` is no longer referenced outside the shared primitive and the session-resolution
      function.
- [x] `ClaimRegistry.factionAlly` is assigned in exactly one place.
- [x] `make dc CMD="./gradlew :server:test"` is green, and `make quick-code-standard` is clean.

**Out of scope:**

- `CommandContext`'s 52 parameters and how commands receive their dependencies — that is [10](10-command-context-deps.md).
- Turning `ClaimRegistry.factionAlly` into a constructor dependency — that is [04](04-gameworld-self-assembly.md).
- The admin HTTP short-circuit that grants access when no token store is configured: it concerns the Account's Admin
  role, not the Character, and must stay a separate rule.
- Renaming `hasPermission`, or merging the Character and Admin role permission catalogs.
- Splitting the Admin role from RBAC groups, tracked in `.scratch/admin-roles/`.
- Populating `groups.yaml` with actual groups; it ships empty and stays that way.

## Answer

Fixed on 2026-09-28 in `1dcc5070`. `Authorizer` (`game/world/claim/Authorizer.kt`) owns the cascade named permission →
owner → Claim (owner, trusted, faction ally, `claim:build`); `EditTarget` is the sealed target type. Block break /
place / interact, Action blocks, Panels, `ClaimManager` and `/actionblock edit` all go through it.
`Claim.canEdit` and `ClaimRegistry.canEdit` are gone.

- `Set<Permission>.grants` is the one "`*` covers everything" primitive; both `hasPermission` helpers delegate to it.
- `resolveSessionPermissions(tokenStore, groupsConfig, groups)` is the single resolution point, used by the direct
  and hub paths (`HubConnection` gained a `groupsConfig` parameter).
- `CommandHandler.isPermittedFor` backs both the visible-command filter and the execution gate.
- `ClaimPermissions.BUILD` / `ADMINISTER` are registered in `PermissionRegistry` and force-loaded in `GameLoop`.
- `ClaimRegistry.factionAlly` has a private setter, assigned only in `bindFactions`.

Deviations from the brief:
- **Unclaimed land stays open** for building and for Action block edits, so `Authorizer` has `canBuildAt` next to
  `isAllowed` (which refuses when no Claim covers the position, the Panel behaviour). `/actionblock edit` therefore
  now accepts any Character on unclaimed land, as the interaction path always did.
- **`canBuildIn` / `canAdminister`** are public next to `isAllowed`: callers that already hold a Claim
  (`ClaimManager`, the block handlers) don't redo the lookup.
- **`PanelManager.canEdit` replaced by `ownerOf`**; the cascade moved to `PanelEditing` through the Authorizer.
- Hub session groups fall back to `groupsConfig.defaultGroups` when the Character has none, like the direct path.

Bug found on the way: `ClaimRegistry.setTrusted` and `reassignOwner` did not reindex `byChunk`, so `claimAt` returned
a stale Claim and a freshly trusted Character could not build until restart. Fixed, with a regression test.

Tests: `AuthorizerTest`, `SessionPermissionsTest`, `HubSessionPermissionsTest`, `CommandGateParityTest`, plus cases in
`ClaimManagerTest` and `ClaimRegistryTest`.
