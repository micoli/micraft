# Perf baseline — `8ca3746c` — 2026-09-26

Two `make perf` invocations on a clean tree (Apple M1 Pro, Chrome headed, 1600×900, world seed 42, NPC seed 42),
plus `make perf-heap` with a full heap snapshot. First baseline with the recalibrated frame budget (long frames),
seeded NPC spawning and the terrain bounds fix (`8ca3746c`: no `Vector3` per vertex). Compared with `33659457`.

## Interpretation

### Validity
- Idle 6/6 and traverse 6/6 windows valid. Traverse travelled 110–134 blocks per 31 s window with 0–2 stuck events
  and no teleport; loaded chunks reached 604–733, so new terrain streamed every window.

### Frame time
- Idle: p50 16.7 ms (60 FPS), p95 18.6 ms (54 FPS), p99 20.5 ms (49 FPS); long frames 0.06 %.
- Traverse: p50 16.7 ms (60 FPS), p95 18.9 ms (53 FPS), p99 23.1 ms (43 FPS), worst window max 50.9 ms (20 FPS);
  long frames 0.48 % (0.27–0.81 %).
- GPU p95 5.9 ms (168 FPS ceiling) idle and 9.4 ms (106 FPS) traversing: still CPU-bound, as in the first baseline.
- Against `33659457`: frame p95/p99 within noise (traverse p99 25.3 → 23.1 ms, −8.5 %, below the 10 % noise bar).

### Render load
- Unchanged: ~837 draw calls idle, ~1 285 traversing, 0.70–0.73 M triangles. One draw call per mesh remains the
  render-side lever.

### Memory
- Client heap, live (after a forced GC, `make perf-heap`): 437 MB at the settled start, **282 MB** after two
  traversals, 301 MB back at the start. Before the bounds fix: 658 / 590 / 638 MB (−52 % after traversals).
- The collector's in-use heap (garbage included) still swings 538 → 1 183 MB between traverse windows: GC timing,
  not growth, and the reason the "heap growth" budget failed (+60 %). The runner now records the live heap at the
  end of each window (after this run) and the budget uses it.
- Full snapshot (533 MB self size, dev bundle):
  | What | Size | Share |
  |---|---|---|
  | 932 `WasmByteArray` (Kotlin): the `blocks` array of each client chunk, 16×16×1025 B ≈ 256 KB | 175 MB | 33 % |
  | `JSArrayBufferData`: CPU copies Babylon keeps of every vertex/index buffer (≈ GPU buffers, 147–175 MB) | 155 MB | 29 % |
  | External strings: script sources (dev `mc_bindings.js` 19.8 MB ×2, Babylon 8 MB ×2); minified in prod | 58 MB | 11 % |
  | Everything else (objects, code, strings, Babylon scene graph) | ~145 MB | 27 % |
- Sampled live allocations (what the run allocated and kept): Kotlin/Wasm 136 MB (73 %), BabylonJS 34 MB.
- Server heap max 506 MB idle / 708 MB traverse, GC share of wall time 0.2 %: not a concern.

### Server tick
- Idle p50 2.6 ms, p99 11.2 ms; traverse p50 3.4 ms, p99 12.6 ms (25 % of the 50 ms budget); 20 TPS. `npc` is still
  the costliest phase (traverse p95 4.7 ms, max 29.3 ms).
- ×2.6 slower than `33659457` at p50 (0.88 → 2.57 ms idle), with identical server code: a run without the NPC seed
  gave the same 2.8 ms, and both invocations of this session agree within 2 %. The difference is the session
  (machine state, core scheduling), so tick deltas are only valid between runs made back to back — now in the skill.

### Budgets
- All ✓ except client heap growth on traverse (+60 %, in-use heap noise, see Memory).

### Stability (2 invocations)
- Stable under 10 %: frame p50/p95, tick p50, draw calls, server heap, idle client heap.
- Noisy: frame p99 idle (13 %), long frames (tiny counts: 0.00 vs 0.22 %), tick p95 idle / p99 traverse (13–15 %),
  in-use client heap traverse (26 %).

## Top findings
1. **The terrain bounds fix halves the live client heap** (590 → 282 MB after traversals) at no frame cost.
2. **Two thirds of what remains is duplicated or empty terrain data**: 175 MB of 1025-block-high chunk arrays,
   mostly air, and 155 MB of vertex data kept on the CPU after upload to the GPU.
3. **Server tick times depend on the session** (×2.6 between two sessions on identical code): only back-to-back
   comparisons are meaningful.
