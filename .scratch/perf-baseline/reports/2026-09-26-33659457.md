# Perf baseline — `33659457` — 2026-09-26

Two `make perf` invocations on the same commit (Apple M1 Pro, Chrome headed, 1600×900, seed 42). Invocation 2 ran
on a tree dirtied only by analysis tooling and GPU-name metadata (no game code), so the runs are comparable. The
GPU name still reads "WebKit WebGL": the WebGPU-based fix landed after these runs.

## Interpretation

### Validity
- Idle: 6/6 windows valid (no movement).
- Traverse: 5/6 valid. Window #6 (invocation 2, heading 270°) travelled 11 blocks with 9 stuck events: steering
  failed against a large obstacle. It is excluded from every figure below. The valid windows travelled 124–133 blocks
  in 31 s (≈ 4.2 blocks/s), and loaded chunks reached 616–739, so new terrain really streamed.

### Frame time (ms and FPS)
| | Idle | Traverse |
|---|---|---|
| average | 16.7 ms (60.0 FPS) | 16.8 ms (59.6 FPS) |
| p50 | 16.7 ms (60 FPS) | 16.7 ms (60 FPS) |
| p95 | 18.4 ms (54 FPS) | 19.1 ms (52 FPS) |
| p99 | 19.8 ms (51 FPS) | 25.3 ms (40 FPS) |
| max (median of windows) | 27.7 ms (36 FPS) | 37.3 ms (27 FPS); worst hitch 111.2 ms (9 FPS) |

- p50 is exactly the display pacing ceiling (the loop is capped at ~14 ms, the 120 Hz screen presents every 2nd
  vsync). **The p95 budget (≤ 16.7 ms / 60 FPS) fails by construction**: any frame that misses one vsync lands at
  ≥ 18–25 ms. About 5 % of frames miss a vsync even at idle.
- **CPU-bound, not GPU-bound**: GPU p95 is 6.5 ms (154 FPS ceiling) idle and 9.4 ms (107 FPS) traversing, far
  below the frame time. The 10–15 ms gap at p99 and the 111 ms hitch are CPU work: the game tick, chunk meshing and
  GC. The JS heap swings of 0.9 → 2.0 GB point at GC pauses.
- Traversal costs +5.5 ms at p99 (51 → 40 FPS): the stutter comes from streaming and meshing new chunks.

### Render load
- ~870 draw calls idle and ~1 250 traversing, with active meshes ≈ draw calls. So there is **one draw call per
  mesh**, with no batching or instancing. `CLAUDE.md`'s old "~200 draw calls" is stale by 4–6×.
- 0.70–0.74 M triangles per frame and ~190 textures, stable. The draw-call count, not the geometry, is the render
  load to attack.
- Idle draw calls vary between invocations (839 vs 1 230, 38 % spread): NPC spawning is unseeded (108–147 NPCs), so
  the scene content differs from run to run.

### Memory
- **Client JS heap is the top concern**: 0.77–0.89 GB idle, and 0.94–2.06 GB while traversing. Growth within an
  invocation is +13 % idle (in 45 s) and +9 % traversing (median), under the 25 % budget. But the absolute level and
  the 1 GB swings are large for a voxel client with a 5×5-chunk view radius. Kotlin/Wasm (WasmGC) objects live
  in this heap.
- Client GPU buffers: 142–178 MB, bounded by the view radius (no growth trend) ✓.
- Server heap: 0.2–0.7 GB with a GC sawtooth. Its max is too noisy to compare runs (see Stability).

### Server tick
- Large headroom: p50 0.9 ms idle and 1.3 ms traversing (2–3 % of the 50 ms budget), p99 7.3 / 11.3 ms, 20 TPS held.
- **Spikes**: max 24 ms idle and 42 ms traversing (median), with a worst case of **82 ms, above the 50 ms tick
  budget**. The `npc` phase drives them: p99 8.5 ms and max 39.9 ms traversing, and it is the costliest phase
  every tick. `players` reaches 13.9 ms max while streaming. `npcLifecycle` (every ~10 s) takes 5.5 ms per run.
- Server CPU is 1–3 % of the machine, and GC 0.1–0.6 % of wall time: the server is nowhere near a bottleneck with
  one Character.

### Budgets
- ✗ Frame p95, in both scenarios. This is structural (vsync pacing, see above), not a regression. The budget should
  change to "p95 ≤ 20 ms (50 FPS)" or be measured as "share of frames > 16.7 ms".
- ✓ Frame p99 < 33.3 ms, ✓ tick p50/p99, ✓ JS heap growth.

### Stability (2 invocations)
- Stable under 10 %: frame p50/p95, average FPS, tick p50, draw calls (traverse), and GPU p95 (traverse).
- Noisy: frame p99 idle 7 % / traverse 5 %; tick p99 13–36 %; client JS heap (traverse) 25 %; server heap max 11–72 %.
  With 15–31 s windows, the tails and the GC-driven memory peaks need 3+ invocations (or longer windows) before a
  delta is conclusive. p50/p95 deltas are usable as is.

## Top findings
1. **Frames are CPU-bound**, with the stutter tail (p99 40 FPS traversing, 111 ms hitch) coming from chunk
   streaming, meshing and GC, not the GPU.
2. **Client JS heap of 0.8–2 GB** with 1 GB swings: the likely source of GC hitches and the biggest memory risk.
3. **One draw call per mesh** (~1 250): batching or instancing is the render-side lever, and the server `npc` phase
   is the tick-side spike source (82 ms worst case).

## Next steps (candidate issues)
- Recalibrate the frame budget (p95 ≤ 20 ms or % of frames missing a vsync), and seed NPC spawning in the perf
  world to cut run-to-run noise.
- Client heap: take a heap snapshot while traversing (what holds 1–2 GB: chunk data copies, mesh arrays, protobuf
  buffers?).
- Per-frame split (tick / mesh drain / GPU upload / render), the deferred part of issue 04, to attribute the CPU time.
- Draw calls: measure the mesh count per chunk and per NPC; evaluate chunk-section merging and NPC instancing.
- Server `npc` phase: profile the spikes (which NPC system: pathfinding, aggro, spawning?).
- Steering: window #6 still got stuck. Consider teleporting ahead when stuck events exceed N in a window.
